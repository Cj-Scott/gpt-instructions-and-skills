# Reference Adaptation

Use references to learn, not to clone.

## Record Each Reference

| Reference | Relevant principle | Product-specific adaptation | Rejected elements | Rights or attribution concern |
| --- | --- | --- | --- | --- |
| | | | | |

Good principles include information hierarchy, density, navigation behavior, content sequencing, responsive transformation, or feedback timing. “Looks premium” is not a principle.

## Adaptation Rules

- Preserve the product's visual thesis, content model, and interaction needs.
- Translate patterns into the project's existing design tokens and component architecture.
- Replace demo content with realistic data before judging hierarchy or density.
- Combine references only when their principles reinforce the same thesis.
- Recreate common interface patterns independently; do not copy proprietary code, branded assets, marketing copy, or a distinctive composition wholesale.
- Verify library licenses and attribution requirements before importing code or assets.
- Treat galleries as inspiration. Do not make external libraries or CodeRabbit mandatory for the workflow.

## Rejection Test

Reject or heavily transform a pattern when:

- It solves a different user job.
- Its appeal depends mainly on the reference brand.
- It adds novelty without improving comprehension or action.
- It conflicts with the product's content density, accessibility, or responsive needs.
- Removing the copied styling leaves no product-specific rationale.
